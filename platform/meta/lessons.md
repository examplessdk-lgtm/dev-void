# Lessons

## Operating Rules

- Branch choice: keep work on the current branch, including `main`, unless the user asks for a separate branch or worktree. Individually reviewable commits do not require a feature branch.
- Worktrees: create real git worktrees with `git worktree add` under `.worktrees/`. Do not apply worktree changes back to the main tree without explicit user confirmation.
- Design/doc work: stay in design mode until the user asks for implementation. If a feature is not live yet, prefer a clean cutover over legacy migration work.
- Docs/progress: code is the source of truth, but public docs may intentionally omit paused features. Describe root scripts exactly as implemented; root `dev` and `build` are dashboard-only. Track "implemented", "shipped", and "done" separately unless the user says they are equivalent.
- Public documentation: follow the writing approach in [Fate's guides](https://fate.technology/guide/requests): introduce one idea, show a small practical example, then explain the resulting behavior. Build up workflows in short sections; keep implementation details in maintainer docs and keep command references easy to scan.
- Commands: avoid HEREDOC commit messages with apostrophes; run `pnpm test <path-or-pattern>` without `--`; from the repository root, use `vp run build:all` for a full SDK + platform build.
- `vp run` argv: unlike `pnpm`, `vp run <script> -- <args>` forwards the literal `--` to the script. For wrangler the `--` separator hides `--env`, so the deploy silently targets the top-level (prod) env. Always write `vp run --filter <pkg> deploy --env production|staging` (no `--` separator), and require production deploys to pass `--env production` explicitly.

## Re-Landing A Stale Branch

- Re-apply, do not rebase, once a branch is a few hundred commits behind. Reversal commits inside the branch (a binding added then removed, an RPC method renamed then reverted) get replayed against ground `main` rewrote, and the hardest file then has to be rewritten inside conflict markers.
- The dangerous drift is the kind git merges cleanly. A signature that GREW parameters is the worst case: converting it to an options object from the branch's old parameter list silently deletes everything `main` added. Rebuild the option type from `main`'s CURRENT signature, then diff the generated output to prove each interpolation survived.
- Give a new option a NAMED home, never a new positional slot. The branch inserted `emailDir` at slot 6 of a 9-argument call with ~68 call sites; every later argument would have shifted by one, and a same-typed shift binds silently. It belonged on the options object the function already took.
- Check whether the branch's hard-coded path still matches `main`'s conventions. The branch used `join(root, 'email')`; `main` had since introduced `readProjectPaths` with a source-root concept, so the branch's version would have broken every project using a `src/` layout.
- When a positional-to-named codemod runs over tests, strip each argument's trailing line comment. `false, // hasQueues` otherwise becomes `remote: // hasQueues`, which still parses, still typechecks, and now documents the wrong parameter.

## Email And Address Routing

- Strip a platform address prefix in exactly ONE place. `createMessageProxy` removed the `<slug>+` prefix so handler authors see the address they wrote, and the generated dispatcher removed it again before matching, leaving an empty tag that no anchored pattern could match. Both halves were individually correct; the seam was untested. Route on the preserved wire address (`__voidPlatformTo`) and let the user-visible field stay stripped.
- Lowercasing an address to match it case-insensitively also lowercases the CAPTURED groups. `support+T-42@` reached the handler as `t-42`, quietly corrupting any case-sensitive tag. Match with the `i` flag against the original string instead.
- A Cloudflare zone setting is not a Cloudflare default. "Subaddressing means a rule for `support@` captures `support+tag@`" was written into the design from the docs' description of the feature; `GET /zones/{z}/email/routing` reads `support_subaddress: false` on every zone we own. Before a design leans on a provider behaviour, read the setting on a real zone.
- "Other tools cannot read wrangler's token" was asserted from the encrypted file on disk without listing wrangler's own commands. `wrangler auth token --json` has been a stable, documented hand-off since 4.57.0, and the encryption is opt-in. Before claiming a tool has no way to do X, read its command table and CHANGELOG — the tool's authors usually solved X already.
- Assert on generated code by RUNNING it, not by searching it for substrings. Every codegen test for the dispatcher passed while it could not route a single real message. Stub the dynamic imports, feed it a message built by the real proxy, and assert which handler ran.

## Framework And Schema

- `void.json` changes must update `packages/void/schema.json`, `docs/config.md`, and related types, validation, or README references.
- Framework DX: preserve existing CLI namespaces, prefer conventions over config, keep advanced hooks as escape hatches, and document clean-break surfaces without migration notes unless asked.
- Adapter/package surfaces: keep runtime APIs at package roots and move Vite plugin factories to explicit `/plugin` subpaths.
- `drizzle-kit push` to `migrate`: seed `drizzle.__drizzle_migrations` from `drizzle/meta/_journal.json` before switching modes.
- Drizzle helpers: on `drizzle-orm@0.45.x`, use `drizzle-zod`, `drizzle-valibot`, and `drizzle-arktype`; infer validators from `db/schema.ts` via `void/drizzle-valibot` and import them from `@schema`.
- SQLite PRAGMA: use bare names or single-quoted strings for `PRAGMA table_info(...)` and `PRAGMA index_list(...)`; do not use double-quoted identifiers.
- Dual SQLite/Postgres paths: keep dialect-specific imports in dialect-specific modules so Workers bundles do not pull `pg` into SQLite/D1 code.
- Database dialect support is end-to-end: widen framework manifests, platform validation and capability negotiation, migration status routing, Hyperdrive URL parsing, and integration tests together.
- Schema deploy safety: migrations must be backward compatible while old code may still run. Additive changes are safe; renames, drops, and type changes need a two-phase rollout. Use `VOID_TEST_DATABASE_URL` for real-Postgres checks and keep `fileParallelism: false`.

## Cloudflare And Deploys

- Workers + CJS bundling: add `esmExternalRequirePlugin` to the actual worker environment in `vite.config.ts`; the env name is the Wrangler worker name, not `"ssr"`.
- Analytics Engine SQL: include `timestamp` when filtering or sorting on it, use `GROUP BY` instead of `DISTINCT`, cast with `toDateTime(...)`, avoid aliasing over `timestamp`, and format datetimes as `YYYY-MM-DD HH:MM:SS`.
- Deploy manifests: `packageBuild` and `packageFrameworkBuild` must include the database binding whenever `bindings.needsD1 || bindings.needsAuth || hasMigrations`.
- Deploy cancellation/dedupe: cancellation is two-phase and must stay blocking until cleanup completes. Only skip worker deploys when worker module hashes are part of the comparison.
- Deploy asset handling: verify client-declared blob hashes against uploaded bytes, stream multipart bodies in the API Worker, and keep the CF WfP cache-buster, early `asset_hashes` persistence, and KV/R2 mirror fallback from design doc 0066.
- API compatibility: dashboard deploys after the platform deploy in the same pipeline, so API changes must stay backward compatible with the currently live dashboard and forward compatible with the dashboard about to deploy. Do not make backwards-incompatible API changes without a staged rollout.
- Void Cloud staging access: CI must set `VOID_API_URL=https://api.staging.void.cloud`; `STAGING=1` is not enough. Staging hosts require Cloudflare Access credentials via `CF_ACCESS_CLIENT_ID`/`CF_ACCESS_CLIENT_SECRET` or `CF_ACCESS_TOKEN`; OAuth callbacks stay Access-bypassed.
- Workers env-var truthy checks: Wrangler env vars are always strings. Guard flags with exact-string equality (e.g. `env.X === 'true'`), never `!env.X` or `Boolean(env.X)` — the latter treats `'false'` and `'0'` as enabled. Pattern lives in `packages/api/src/env.ts` (`isDevBypass`).
- `wrangler dev` mangles `Location: http://localhost:*` redirects: it prepends the dev origin port to the host (e.g. `Location: http://localhost:5173/x` arrives as `localhost:8787:8787:5173/x`, producing `ERR_INVALID_REDIRECT` in Chrome). `127.0.0.1` and other hostnames are not affected; `https://` is not affected. When an API endpoint must redirect a browser to another `localhost:port`, return `200 OK` with an HTML body containing `<script>location.replace(...)</script>` instead of a 30x. Vitest `app.fetch` bypasses wrangler, so test the embedded target string, not the Location header. Pattern lives in `packages/api/src/routes/auth.ts` (`/auth/dev-login`).
- WfP DO namespace lookup: do not poll account-wide DO namespace lists. Use `GET /workers/dispatch/namespaces/{ns}/scripts/{script}/bindings` and read the binding `namespace_id`.
- WfP DO dispatch: do not call service-binding `.fetch` from inside a `DurableObject` or `WorkerEntrypoint` subclass; enqueue to a Queue or dispatch from a non-DO worker instead.
- Cron sync: run cron DO `/sync` or `/clear` only after routing has switched so pre-cutover deploy failures cannot disable the previous live deployment's crons.
- CF duplicate-recovery lookups: when a route adds a follow-up Cloudflare lookup after a caller-visible error such as 409, wrap that lookup separately so CF 429 still passes through for retry/backoff and other lookup failures fall back to the original caller-visible error instead of becoming a generic 500.
- Container provisioning: the platform must create container applications itself, POST with `durable_objects.namespace_id`, omit immutable fields on PATCH, treat 409 as concurrent create, and verify namespace matches before PATCH.
- WfP container lifecycle: WfP scripts cannot cross-bind to each other with `script_name`, so the platform uses per-deploy container DO ownership. One DO namespace can back at most one container app, and deleting a WfP script does not delete the app; cleanup must delete container apps explicitly.
- Build-container child env: a build container is a CI environment and must say so. Set `CI=true` (the exact string — `@clack/prompts`' `isCI` compares by identity, so `'1'` silently does nothing) on every child, or interactive CLIs animate into piped stdio: `ESC[1G ESC[J` frame separators with no newline collapse an entire spinner run into ONE captured log line. `github_actions` builds hide the bug because the runner sets `CI` for you.
- Log capture vs. log render: strip ANSI at RENDER time, not at capture. A terminal consumes escapes, a markdown fence prints them — but the live tail and `void build logs` want the color. Sanitize before any byte-budget accounting, or erased frames nobody can see will evict the real output.
- Do not build a classifier or a second terminal model when a maintained emulator already owns the state machine. The log sanitizer shipped repeated semantic omissions around erase direction, cursor repositioning, scrollback erase, tab stops, protected cells, C0/C1 transitions, and intermediate-bearing commands. `@xterm/headless` provides that screen state; the surrounding code should only impose deterministic resource bounds before untrusted input reaches handlers whose work is amplified by `Ps`. A tokenizer or ANSI stripper is insufficient because the visible result depends on cursor and cell state, while a `performance.now()` cutoff is ineffective in Workers because the clock does not advance during CPU work.
- Pick an oracle that actually implements the thing you are testing, and check that before citing it. The sanitizer's tests cite pyte as "ground truth from a real VT emulator". It cost two separate wrong answers: pyte implements OSC only, with no DCS/SOS/PM/APC handling, so it reproduces the string-control bug those cases exist to catch; and its `erase_in_display` hardcodes `how == 2 or how == 3`, so it reports `ESC[3J` as a full-screen erase when a real terminal drops scrollback and touches no visible cell. Both times a green test certified the wrong behavior, and the second was written by the round of review that fixed the first. Use `@xterm/headless` (full VT500 parser) for anything outside pyte's model. A green test against a blind oracle is worse than no test — it is an argument for the bug.
- Only `ctx.storage` operations hold a Durable Object's input gate. Non-storage I/O — `fetch()` (a container port fetch included), KV, Hyperdrive — OPENS the gate and lets another event interleave. So a helper that reads shared state, awaits non-storage I/O, then writes that state back is safe only while it has exactly ONE caller; the moment a second entry point can reach it (an RPC, a teardown path), it needs a single-flight gate (`inFlight ??= run().finally(() => { inFlight = null; })`) or `blockConcurrencyWhile`. The DO log pull read `logCursor`, fetched, and wrote it back three awaits later; adding a teardown drain gave it a second caller, and every cancel that overlapped a scheduled poll double-ingested the same lines — stored twice, broadcast twice, and charged twice against the bounded log/tail budgets.
- A pull-based log transport needs a producer-side drain barrier. If the only path to the sink is the consumer polling the producer, then everything produced after the last poll dies with the producer — and the loss is worst exactly when it matters most, because a fast failure fits entirely inside one poll interval. Have the producer hold itself open until the consumer's acknowledged cursor catches up; a later request carrying `since=N` proves durable consumer-side ingestion when the consumer advances that cursor only after parse and insert. A write-completion callback certifies only the producer side. Use a short idle deadline that resets only on monotonic acknowledgement progress plus a non-resettable absolute cap: one fixed deadline either loses a productive multi-callback drain or pins every dead peer for too long. Any timeout armed against the producer must cover execution plus the absolute drain window. On forced teardown, revoke authority first, then single-flight the entire join → fresh drain → liveness recheck → signal sequence; gating only the pull still admits a late concurrent pull after the termination marker.
- When you assert an early-out is correct, check the state it is early-outing on is reachable. A test drove `onStop` (fires only because the container exited) against a stub that still reported the container running, so it asserted "no final pull" for a state production cannot produce — and that green test was the reason the tail-loss bug looked like intended behavior. Split it: one test per genuinely reachable state.
- A test that builds HALF a state asserts the bug. `emits no marker from a cancel that did not terminalize the row` set up its "peer teardown already ran" premise with `setStatus('failed')` alone — but a real peer claims the termination marker SYNCHRONOUSLY, one line before it sets that status. The setup therefore constructed `terminal status + live container + marker unclaimed`, which no teardown can produce, and then demanded silence for it — locking in a bug where a cancel arriving after `onError` SIGKILLed a live container and wrote no explanation. When a test fakes a state some other code path normally produces, enumerate everything that path writes and write ALL of it, or drive the real path.
- A deadline that bounds a WAIT does not bound the WORK. `withDeadline` rejects the promise; the Postgres UPDATE behind it keeps running and usually commits afterwards. So repairing the miss by re-reading the row ONCE, immediately, only covers the ordering where the commit beat the read — the likelier ordering (commit lands after) reads an ACTIVE row, concludes nothing, and then goes unnoticed forever because the local terminal status early-outs every retry. Drive reconciliation off the work's ACTUAL settle, or off a re-armed check that self-terminates; and before calling something a fallback, confirm it does the thing you need — the stale reaper terminalizes the ROW but never completes a CHECK RUN.
- Cross-package "keep in sync" comments do not hold. `PINNED_VOID_CLI_VERSION` drifted a full minor because the only thing enforcing it was a comment, and the path it guards (repos with no local `void` dep) is exercised by almost no build. Assert the equality in a test instead.
- Terminal escape parsing has a 7-bit form AND an 8-bit form. Decoded build output can carry U+009B (CSI), U+009F (APC), U+0090 (DCS) directly; matching only `ESC`-prefixed sequences let whole sequences and entire binary payloads through as visible text. Normalise every C1 (U+0080–U+009F) to `ESC <char>` once, then parse one shape.
- `ESC <char>` is not a fixed two bytes. The real grammar is `ESC <intermediates 0x20–0x2F> <final 0x30–0x7E>`, so terminfo's `sgr0` (`ESC ( B`) printed a stray `B` on every colourised build. Parse to the final byte.
- When a reviewer's claim is mechanically checkable, check it mechanically before writing a fix. Four of five sanitizer findings reproduced verbatim against the xterm oracle in one run; the fifth ("exclusive mutation endpoints") was a misread of a guard that already did the right thing, and would have cost a regression to "fix".
- Widening a fuzz's alphabet finds bugs a new named case cannot. Adding one wide-glyph-plus-combining-mark atom surfaced a real orphaned-continuation-marker bug in the write path that no reviewer reported and no hand-written case covered.
- A byte budget must count the bytes that actually go on the wire. `entry.line.length` is UTF-16 code units; JSON escaping (6 bytes per control char), UTF-8 (3 bytes per BMP CJK unit) and per-object envelope made a 2 MiB cap admit a 12.1 MiB body. Budget `Buffer.byteLength(JSON.stringify(entry))`.
- A page cap bounds WORK, not LATENCY. Giving each page its own timeout leaves the loop unbounded (32 x 2s = 64s in one callback). When a loop sits in front of a signal or a serial scheduler, give the whole loop one wall-clock deadline and let it resume next tick.
- And the converse: a wall-clock deadline bounds LATENCY, not WORK — in a Worker it cannot bound work at all, because the clock advances on I/O and stands still during CPU. The whole-drain deadline added for the point above measured only the agent's response time and scored every JSON parse, SQLite insert and WS fan-out between the fetches as free. Both bounds are needed, and the work one must be counted in the INPUT: charge rows AND payload bytes AND fan-out width (`(1 + subscribers) * max(1, ceil(len / 1024))`), because the producer caps a page in BYTES, so two 1 MiB lines are a full page that a row-count budget prices at 2. Check the budget between atomic units, never inside one, so the cursor never advances past work that did not happen.
- Capping a buffer by line COUNT does not cap its SIZE. 10000 x 128 KiB is 1.22 GiB. If a consumer's budget is in bytes, the producer's cap has to be too, or coverage is average-case rather than guaranteed.
- Trim an evicting buffer to a low-water mark, not to the cap. Landing exactly on the cap makes the next insert evict again, so the cost stops being amortized — and in tests it silently shifts the indices later cases slice from.
- Bounding a data structure's SIZE does not bound the WORK done on it. Row-shifting terminal commands (DCH/ICH) cost N x L where N and L both come from the same untrusted line — quadratic, on a row that never grows. Three separate routes (huge allocation, quadratic regex, quadratic memmove) reached the same DO-CPU hazard; bound cost in the INPUT, not just the result.
- Measure the reviewer's perf claim before accepting its number. The reported 4.9s was 20.6s at the real capture cap, which moved it from 'slow' to 'takes the DO out'.
- Two caps that must be compared have to be in the SAME unit. Capping a producer's buffer in UTF-16 code units while the consumer's budget is in serialized bytes turns a structural guarantee back into an average-case one — the 6x JSON-escape factor is exactly the gap. Fixing one side of a unit mismatch and not the other is its own bug.
- Capturing log fixtures: `gh api` rewrites control bytes to caret notation (`^[`), so an escape-handling fix looks like a no-op against a fixture captured that way. Use `curl -H "Authorization: Bearer $(gh auth token)"` for true bytes.
- DO migrations: preserve chronological migration tag order across features and use configured class/binding names. On re-PUT, read nested `script.migration_tag`; if it already equals the target, omit `migrations` because resending the same `new_tag` returns CF 10079.
- Stacked review follow-ups: when the user supplies a worktree and a PR that point at different stacked branches, reconstruct the full stack before classifying the newest comments. Read both PR descriptions, the commit sequence, prior resolved threads and replies, and the end-to-end producer/consumer invariants first; only then decide which branch owns each fix and where it must be applied.

## Product Surfaces

- `void project logs`: Cloudflare Tail only sees top-level `console.*` and uncaught throws. Surface caught app errors with `console.error` or `void/log` `logger.error(...)`. `--filter` is message substring search; use `--level` for severity filtering.
- Local dashboard testing: use the local API or an explicitly configured installation. Its deployed API may not yet expose new fields; keep development bypasses confined to local configuration.
- Dashboard Worker local env: if `packages/dashboard/.dev.vars` exists, put local Worker vars such as `API_URL` and `SITE_DOMAIN` there or in `wrangler.jsonc` vars.
- Dashboard staging OAuth: verify the generated `dist/ssr/wrangler.json` and Wrangler dry-run bindings after a staging build; callback auth codes must tolerate Cloudflare Access interposition between API and dashboard callbacks.
- Dashboard Tailwind colors: `packages/ui/src/styles/tokens.css` resets the palette with `--color-*: initial`; define needed scales in `@theme` before using utilities such as `bg-gray-*`.
- Requests Analytics Engine queries should consistently key projects by `blob1`; dispatch also writes `index1`, but billing and top-traffic queries use `blob1`, so dashboard traffic summaries should match that established path.
- Dashboard marketing shells: use a column `min-h-screen` layout with the page area as `flex-1`, so `FooterNav` sits at the viewport bottom. Keep shared `.wrapper` at `w-full` because flex children with `mx-auto` can otherwise shrink to their content. When page content is shorter than the viewport, fill the leftover middle slot with a flexible empty `.wrapper` so the side borders continue down to the footer.
