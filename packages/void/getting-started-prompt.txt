Void is a fullstack Vite framework and deployment platform for Cloudflare.
Deployment connection: `void connect` chooses Cloudflare or a Void platform and signs in when needed. Use `void connect --platform cloudflare` to select a Cloudflare account, or `void connect <url>` to join a company platform. Existing project links are preserved when connecting elsewhere. `--no-login` registers a verified Void platform without authentication; authenticated headless connection requires a valid origin-scoped keychain session or `VOID_TOKEN` with matching `VOID_API_URL`. Platform installation and administration use `void platform`.
Non-interactive self-hosted platform lifecycle mutations require `--yes`; `--plan` is read-only and needs no acknowledgement. Published routes and custom domains are observed for recovery but retained for explicit dashboard cleanup because Cloudflare cannot condition deletion on an immutable attachment generation.
If you are administering an installed platform, use `void platform auth login`
for a separate, revocable administrator session. The `user`, `project`,
`deployment`, `build`, `signup`, `invitation`, and `system` groups under
`void platform` provide terminal administration. Read their `--help`; use
`--plan` before changes, `--yes` for approved noninteractive mutations, and
`--json` for scripts. Operator commands select the active connection or explicit
`--connection`/`VOID_API_URL`, never an application's project file. Automation
uses `VOID_OPERATOR_TOKEN` from a secret manager with an explicit origin.

In an empty directory, set up a new app like this:

npm install -D void

Then run:

npx void init

In an empty directory, `void init` will add the matching Pages adapter and starter dependencies after you choose a scaffold toolchain and framework. Vite+ is the default toolchain. In an existing app, it configures Void in place by adding missing Vite scripts and creating or patching `vite.config.*` with `voidPlugin()`.

During `void init`, choose Vite+ unless you specifically want plain Vite scripts, then choose a Pages framework (React, Vue, Svelte, or Solid). Choose D1 for a zero-config default, PostgreSQL for existing Postgres, or MySQL for existing MySQL-compatible infrastructure.

At the end of the interactive flow, `void init` asks for Cloudflare (default), Void, or Skip deployment setup and saves the choice in `.void/project.json`. Choosing Cloudflare creates or augments `wrangler.jsonc`, handles secure browser sign-in through Void's bundled tooling, and saves the selected `account_id`. Void-managed deployment requires an explicit platform: connect with `void connect <url>`, or preview and install a company control plane with `void platform install --plan` and `void platform install`. Your first app deploy is then just:

void deploy

For a self-hosted company platform, interactive administration uses Cloudflare browser OAuth with system-keychain storage, while the installed control plane receives a separate scoped runtime API token. Provide a dedicated empty PostgreSQL database; the installer transactionally claims it for that installation, uses the claim to serialize lifecycle changes across hosts, and stores a secret-free authoritative lifecycle manifest in the claimed row. Local recovery material is AES-256-GCM encrypted with an OS-keychain key. After discovery on a new machine, export `VOID_PLATFORM_DATABASE_URL`; normal upgrades preserve deployed Worker secrets, while recreating a missing Worker requires restoring its original runtime, GitHub, R2, JWT, and project-encryption secrets. Void never regenerates those keys for an existing installation. `void platform disable [id]` gates installation-owned traffic through routing storage across repair and upgrade; use `void platform enable [id]` to restore it explicitly. Lifecycle redeploys preserve unrelated routes and custom domains, including rollback state, and refuse to proceed when Hyperdrive no longer points at the pinned database. Platform upgrades verify packaged SQL and the live migration prefix, require an explicit rollback-compatible source-version/schema edge before pending SQL, apply it transactionally, and retain the old Worker version until target health passes. Install, upgrade, repair, and enable accept `--runtime <directory>` for a source-built runtime; it follows the same integrity and rollback path as packaged artifacts, and records `VOID_PLATFORM_SOURCE_REVISION` when set during the build. Lifecycle changes verify the remote installation and per-resource ownership before mutating Cloudflare. Safe uninstall always retains name-addressed Workers, R2, AI Gateway, external PostgreSQL, and zones for explicit manual cleanup.

To override the saved choice, use `void deploy --platform cloudflare` or `void deploy --platform void`. Cloudflare supports full Void Workers; static sites, SPAs, known SSGs, `--dir`, and fully prerenderable `output: "static"` Pages apps; and Cloudflare output from TanStack Start, React Router, vinext App Router and Pages Router, SvelteKit, Nuxt, Analog, and Astro. Hybrid/SSR apps keep their generated Worker, while static deployments use a thin shared edge Worker. Worker apps automatically create or adopt D1/KV/R2/Queues/Hyperdrive resources and configure typed state and WebSocket routes as SQLite-backed Durable Objects. Custom D1 migration layouts are accepted only when Cloudflare's exact file set and order match the migration set Void validated. Keys marked `.secret()` become encrypted Worker secrets; auth deploys preserve or create a persistent `BETTER_AUTH_SECRET`; PostgreSQL/MySQL deploys read `DATABASE_URL` only from the shell. Direct deploy uploads a Worker Version, probes it before traffic, activates it at 100%, and synchronizes triggers with automatic restoration on failure. Versions without previews are staged at 0% and probed through workers.dev with a version override; the same safe fallback applies when Access blocks a generated preview alias but admits the stable Worker hostname. Set `CLOUDFLARE_WORKERS_SUBDOMAIN` in fresh CI, while local deploys cache it automatically. When Cloudflare Access protects `workers.dev`, export an admitted `CF_ACCESS_CLIENT_ID` / `CF_ACCESS_CLIENT_SECRET` service-token pair for CI or a short-lived `CF_ACCESS_TOKEN` from `cloudflared` locally. With Cloudflare saved, `void secret`, `void domain`, `void project status|logs|rollback`, and remote `void db` commands target the pinned Worker or D1 database; logs are live tails and rollback never reverses database migrations. `void init --github` creates a Cloudflare workflow that requires a scoped `CLOUDFLARE_API_TOKEN`. Direct commands target the top-level root Cloudflare config only; named environments, worker-bearing `--skip-build`, and node/bun/deno deploy targets fail closed. Avoid concurrent first deploys from different hosts because provisioning locks only the local config path.

For strongly consistent per-key state, add `durable-objects/counter.ts` and named- and default-export the same `defineDurableState()` value from `void/durable`. Void derives the binding, worker class, and SQLite-backed Cloudflare migration from the filename; call typed RPC methods with `Counter.get(name)`. This works in native Void apps on Cloudflare and with direct Cloudflare deploys. Typed state and `*.ws.ts` WebSocket routes both work with direct Cloudflare deploys.

Database workflow: define Drizzle tables in `db/schema.ts`, import `db` from `void/db` and tables from `@schema`. Use `void db push` to prototype (applies schema directly, no migration files). Use `void db generate` when ready to create production migration files in `db/migrations/`; when Void-managed auth is enabled, it automatically includes the production Better Auth tables, including configured renames and plugin tables. Review and commit the migration before deploying. `drizzle-orm` and `drizzle-kit` ship with void — no extra install needed. Scaffold new tables with `void gen model <name> [columns...]`.

MySQL uses `"database": "mysql"`, builders from `void/schema-mysql`, and Hyperdrive in production. PostgreSQL and MySQL direct deploys read the production `DATABASE_URL` from the shell; PostgreSQL migrations are transactional, while MySQL DDL is not.

Connect an existing external database with `void db connect <connection-string>`, or provision Neon with `NEON_API_KEY=... void db connect --provider neon`. This saves `.env.local` and syncs a linked Void project unless `--local-only` is passed. Custom adapters implement `DatabaseProviderAdapter` from `void/database-provider`.

Email: send transactional mail with `import { sendEmail } from "void/email"`. On the platform every project gets a sender — `<project-slug>+noreply@mail.void.cloud` — which is used when you omit `from`; a custom sender domain is not supported there yet. On `void deploy --platform cloudflare` (your own Cloudflare account), set `email.from` in `void.json` to an address on a zone you own and the first deploy prints a checklist, asks once, then enables Email Routing, writes the `SEND_EMAIL` binding and the `addresses` array into `wrangler.jsonc`, and routes each `email/` handler's address to your worker (in CI, run `void email setup --platform cloudflare` once, commit `wrangler.jsonc`, and deploy with `--require-email`). Add recipients with `void email allow <address>` (Cloudflare emails them a verification link) and list them with `void email destinations`. Receive inbound mail by dropping `defineEmail()` handlers in the top-level `email/` directory (e.g. `email/support+[ticket].ts`) — Void apps only; under TanStack Start, React Router, SvelteKit, Nuxt, Analog or Astro an `email/` directory is a build error, while `sendEmail` keeps working. Check quota and activity with `void email usage` and `void email logs`; during `void dev` sends are captured by the local inbox at `/__void/inbox` instead of being delivered — in Void apps and Class A framework apps (TanStack Start, React Router). Class B/C integrations (SvelteKit, Nuxt, Analog, Astro) run their own dev server, so the inbox is not installed there and sends return `BINDING_MISSING`; use `createEmailTestHarness` from `void/email/testing`, which captures in-process everywhere.

Routing extras: declare static redirects/rewrites/fallbacks in `void.json` under `routing.*`, or in a `public/_redirects` file. For dynamic rewrites, call `c.rewrite(path)` in a `defineMiddleware`.

Logs: surface app-level errors via `import { logger } from "void/log"` and `logger.error(msg, fields?)` (also `.warn` / `.info`) so they appear under `void project logs --level error`. Errors only persisted to your own DB are invisible to Cloudflare Tail. Logs only exist where a worker ran — for 5xx generated by the edge router or on static/SPA projects, use `void project requests --status 5xx` instead.

CI / fresh clones: run `void prepare` after install to generate `.void/routes.d.ts`, `.void/db.d.ts`, `.void/queues.d.ts`, `.void/env.d.ts`, and `.void/tsconfig.json` without booting Vite. `vite dev` / `vite build` populate these during normal app workflows.
