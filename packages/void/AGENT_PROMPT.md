## Void

This project uses [Void](https://void.cloud) — a fullstack Vite plugin + deployment platform for Cloudflare. `voidPlugin()` in `vite.config.ts` gives you file-based API routing on Hono (`routes/`), Inertia-inspired server-rendered pages with co-located loaders/actions (`pages/` + `@void/vue` or `@void/react`), auto-provisioned D1/KV/R2 bindings, typed Durable Object state, first-class Drizzle ORM integration (schema in `db/schema.ts` -> `void/db` Drizzle instance -> typed routes -> typed fetch client), built-in auth, queues, cron jobs, email (`void/email` for outbound in every project; an `email/` directory for inbound handlers in Void apps only — under a third-party framework that directory is a build error; on `void deploy --platform cloudflare`, set `email.from` in `void.json` and the first deploy sets Email Routing and the `SEND_EMAIL` binding up on your own zone after one confirmation), edge caching (ISR), and one-command deploys via `npx void deploy`. For first-time setup, prefer `npx void init`; in an empty directory, install `void` first and let the interactive flow scaffold the starter with Vite+ by default, add the matching framework adapter, configure project files, handle auth, and link or create the deploy project before the first deploy. In an existing app, `void init` configures Void in place by adding missing Vite scripts and creating or patching `vite.config.*` with `voidPlugin()`. Use `void` and `@void/*` package names in source code and package manifests.

Database: define Drizzle tables in `db/schema.ts`, import `db` from `void/db` and tables from `@schema`. Use `void db push` for prototyping, `void db generate` for production migrations. When Void-managed auth is enabled, generation automatically includes its production Better Auth tables (including config renames/plugins); do not duplicate them in `db/schema.ts`. `drizzle-orm` and `drizzle-kit` ship with void (no extra install). Migrations live in `db/migrations/`.

Database dialects: omit `database` for D1, use `"database": "pg"` for PostgreSQL, or `"database": "mysql"` for MySQL. External databases use `DATABASE_URL` locally and Hyperdrive in production. Import builders from `void/schema-d1`, `void/schema-pg`, or `void/schema-mysql` to match. Direct Cloudflare deploy applies checked-in PostgreSQL/MySQL migrations using the shell-provided production URL; PostgreSQL is transactional, MySQL DDL is not.

Durable state: create `durable-objects/name.ts`, named- and default-export the same `defineDurableState()` value from `void/durable`, and call typed RPC methods through `State.get(id)`. Void derives the binding, worker class, and SQLite-backed Cloudflare migration from the filename. This supports native Void apps on Cloudflare, including direct Cloudflare deploys, and is separate from legacy `*.ws.ts` routes.

External database setup: use `void db connect <connection-string>` to update `.env.local` and a linked Void project, or `NEON_API_KEY=... void db connect --provider neon` to provision Neon. Pass `--local-only` to avoid remote sync. Custom provider modules export a `DatabaseProviderAdapter` from `void/database-provider`.

Env: declare every env key in `env.ts` at the project root via `defineEnv({ KEY: string(), ... })` from `void/env`. Read values via `import { env } from "void/env"`. Schema validation runs at dev start (warns) and on `void deploy` (hard error on missing prod secrets). Use `VITE_*` prefix for keys that should be exposed to client code.

CI/editor prep: run `void prepare` to generate `.void/routes.d.ts`, `.void/db.d.ts`, `.void/queues.d.ts`, `.void/env.d.ts`, and `.void/tsconfig.json` without booting Vite. Run it after `npm install` in CI or a fresh clone before typechecking; `vite dev` and `vite build` regenerate these during normal workflows.

Rewrites and redirects: declare static rules in `void.json` under `routing.redirects` / `routing.rewrites` / `routing.fallbacks`, or in a `public/_redirects` file. For dynamic rewrites, call `c.rewrite(path)` in a `defineMiddleware`.

Logs: surface app-level errors that should show up under `void project logs --level error` via `import { logger } from "void/log"` and `logger.error(msg, fields?)` (also `.warn` / `.info`). Anything caught and only persisted to your own DB is invisible to Cloudflare Tail; route it through `logger.*` or `console.*` so the platform can see it.

Requests: `void project logs` only has rows when a worker actually ran. 5xx generated by the edge router, and every request to a static/SPA project, produce no log line at all. Use `void project requests --status 5xx --range 12h` to see those — it lists status, method, and duration for every request the edge served, whether or not a worker was invoked.

Deploy platform: `void init` asks for Cloudflare (default), Void, or Skip and saves `platform` in `.void/project.json`. Choosing Cloudflare creates or augments `wrangler.jsonc`, offers Wrangler login, and saves the selected `account_id`; choosing Void can handle Void auth and project linking. `void deploy` uses the saved choice; `--platform cloudflare` and `--platform void` override it without changing project config, while the legacy `--backend cloudflare` alias remains supported. The Cloudflare path automatically creates or adopts the D1/KV/R2/Queues/Hyperdrive resources the source needs and configures inferred SQLite Durable Objects, then continues the deploy. Keys explicitly marked `.secret()` in `env.ts` are removed from plaintext vars and uploaded as encrypted Cloudflare Worker secrets; values may come from `.env`, `.env.production`, `.env.production.local`, or the deploy process environment. Unmarked local and shell values are excluded. For auth-enabled apps on either platform, deploy preserves an existing `BETTER_AUTH_SECRET` or creates a persistent encrypted secret when missing; bare Wrangler deploys require manual secret setup. It uses local wrangler auth, so if init could not save an account, run `wrangler login` and rerun `void init`, or set `account_id` in `wrangler.jsonc` / `CLOUDFLARE_ACCOUNT_ID`. PostgreSQL provisioning and direct-deploy migrations read the production `DATABASE_URL` from the shell, never from `.env*`, and never serialize it into the Worker config. v1 supports full Void apps on the Cloudflare Workers target only (D1/KV/R2/Queues/Hyperdrive, typed SQLite-backed Durable State, auth, and ISR); framework SSR of every kind (TanStack Start, React Router, vinext, SvelteKit, Nuxt, Analog, Astro), static/SPA/SSG apps (including `output: "static"`), legacy key-value-backed WebSocket routes (`*.ws.ts`), a custom `migrations_pattern`, and node/bun/deno targets fail closed with guidance. For auth apps, `void db generate` includes the production Better Auth schema; commit that migration and Cloudflare deploy validates and applies it. Avoid concurrent first deploys from different machines or CI runners because provisioning locks only the local config path.

Full docs are in `node_modules/void/docs/`. If you have the `void` skill available, use it for a complete API reference covering project structure, routing, pages mode, database, auth, typed fetch, KV, storage, queues, cron jobs, email, CLI, configuration, and deployment.
