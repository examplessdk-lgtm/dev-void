## Void

Non-interactive self-hosted platform lifecycle mutations require `--yes`; `--plan` is read-only and needs no acknowledgement. Published routes and custom domains are observed for recovery but retained for explicit dashboard cleanup because Cloudflare cannot condition deletion on an immutable attachment generation.

Use Void commands for every user-facing workflow. Do not ask users to install, authenticate, or run Wrangler directly. Refer to Cloudflare or Void instead, except when naming literal `wrangler.jsonc` / `wrangler.json` files or `WRANGLER_*` environment variables they must inspect.

This project uses [Void](https://void.cloud) — a fullstack Vite plugin + deployment platform for Cloudflare. `voidPlugin()` in `vite.config.ts` gives you file-based API routing on Hono (`routes/`), Inertia-inspired server-rendered pages with co-located loaders/actions (`pages/` + `@void/vue` or `@void/react`), auto-provisioned D1/KV/R2 bindings, typed Durable Object state, first-class Drizzle ORM integration (schema in `db/schema.ts` -> `void/db` Drizzle instance -> typed routes -> typed fetch client), built-in auth, queues, cron jobs, email (`void/email` for outbound in every project; an `email/` directory for inbound handlers in Void apps only — under a third-party framework that directory is a build error; on `void deploy --platform cloudflare`, set `email.from` in `void.json` and the first deploy sets Email Routing and the `SEND_EMAIL` binding up on your own zone after one confirmation), edge caching (ISR), and one-command deploys via `npx void deploy`. For first-time setup, prefer `npx void init`; in an empty directory, install `void` first and let the interactive flow scaffold the starter with Vite+ by default, add the matching framework adapter, configure project files, handle auth, and link or create the deploy project before the first deploy. In an existing app, `void init` configures Void in place by adding missing Vite scripts and creating or patching `vite.config.*` with `voidPlugin()`. Use `void` and `@void/*` package names in source code and package manifests.

Database: define Drizzle tables in `db/schema.ts`, import `db` from `void/db` and tables from `@schema`. Use `void db push` for prototyping, `void db generate` for production migrations. When Void-managed auth is enabled, generation automatically includes its production Better Auth tables (including config renames/plugins); do not duplicate them in `db/schema.ts`. `drizzle-orm` and `drizzle-kit` ship with void (no extra install). Migrations live in `db/migrations/`.

Database dialects: omit `database` for D1, use `"database": "pg"` for PostgreSQL, or `"database": "mysql"` for MySQL. External databases use `DATABASE_URL` locally and Hyperdrive in production. Import builders from `void/schema-d1`, `void/schema-pg`, or `void/schema-mysql` to match. Direct Cloudflare deploy applies checked-in PostgreSQL/MySQL migrations using the shell-provided production URL; PostgreSQL is transactional, MySQL DDL is not.

Durable state: create `durable-objects/name.ts`, named- and default-export the same `defineDurableState()` value from `void/durable`, and call typed RPC methods through `State.get(id)`. Void derives the binding, worker class, and SQLite-backed Cloudflare migration from the filename. This supports native Void apps on Cloudflare, including direct Cloudflare deploys, and is separate from legacy `*.ws.ts` routes.

External database setup: use `void db connect <connection-string>` to update `.env.local` and a linked Void project, or `NEON_API_KEY=... void db connect --provider neon` to provision Neon. Pass `--local-only` to avoid remote sync. Custom provider modules export a `DatabaseProviderAdapter` from `void/database-provider`.

Env: declare every env key in `env.ts` at the project root via `defineEnv({ KEY: string(), ... })` from `void/env`. Read values via `import { env } from "void/env"`. Schema validation runs at dev start (warns) and on `void deploy` (hard error on missing prod secrets). Use `VITE_*` prefix for keys that should be exposed to client code.

CI/editor prep: run `void prepare` to generate `.void/routes.d.ts`, `.void/db.d.ts`, `.void/queues.d.ts`, `.void/env.d.ts`, and `.void/tsconfig.json` without booting Vite. Run it after `npm install` in CI or a fresh clone before typechecking; `vite dev` and `vite build` regenerate these during normal workflows.

Rewrites and redirects: declare static rules in `void.json` under `routing.redirects` / `routing.rewrites` / `routing.fallbacks`, or in a `public/_redirects` file. For dynamic rewrites, call `c.rewrite(path)` in a `defineMiddleware`.

Logs: surface app-level errors that should show up under `void project logs --level error` via `import { logger } from "void/log"` and `logger.error(msg, fields?)` (also `.warn` / `.info`). Anything caught and only persisted to your own DB is invisible to Cloudflare Tail; route it through `logger.*` or `console.*` so the platform can see it.

Requests: `void project logs` only has rows when a worker actually ran. 5xx generated by the edge router, and every request to a static/SPA project, produce no log line at all. Use `void project requests --status 5xx --range 12h` to see those — it lists status, method, and duration for every request the edge served, whether or not a worker was invoked.

Deploy platform: `void init` asks for Cloudflare (default), Void, or Skip and saves `platform` in `.void/project.json`. Choosing Cloudflare creates or augments `wrangler.jsonc`, handles secure browser sign-in through Void's bundled tooling, and saves the selected `account_id`; Void deployment requires an explicit platform connection (`void platform connect <url>`) or a company installation (`void platform install --plan`, then `void platform install`). One connection auto-selects, multiple connections prompt, and non-interactive use must select explicitly. `void deploy` uses the saved choice; `--platform cloudflare` and `--platform void` override it without changing project config, while the legacy `--backend cloudflare` alias remains supported. The Cloudflare path supports full Void Workers; static sites, SPAs, known SSGs, and `--dir`; fully prerenderable `output: "static"` Pages apps; and Cloudflare builds from TanStack Start, React Router, vinext App Router and Pages Router, SvelteKit, Nuxt, Analog, and Astro. Hybrid/SSR apps retain their application Worker; static assets run behind a thin shared edge Worker. Worker apps automatically create or adopt D1/KV/R2/Queues/Hyperdrive resources and configure inferred typed-state and WebSocket classes as SQLite Durable Objects. Custom D1 migration directories, tables, and patterns are accepted only when Cloudflare's exact file set and numeric order match the migrations Void validated. Keys marked `.secret()` in `env.ts` become encrypted Worker secrets; auth-enabled deploys preserve or create a persistent encrypted `BETTER_AUTH_SECRET`. PostgreSQL/MySQL provisioning and migrations read `DATABASE_URL` only from the deploy shell. Direct deploy uploads an immutable Worker Version, probes it, activates it at 100%, synchronizes triggers, and restores the previous version if readiness or trigger sync fails. Durable Object versions without preview URLs are staged at 0% and probed with a workers.dev version override; the same safe fallback applies when Access blocks a generated preview alias but admits the stable Worker hostname. Set `CLOUDFLARE_WORKERS_SUBDOMAIN` in fresh CI, while local deploys cache it automatically. If Cloudflare Access protects the Worker's `workers.dev` hostname, supply an admitted `CF_ACCESS_CLIENT_ID` / `CF_ACCESS_CLIENT_SECRET` service-token pair for CI or a short-lived `CF_ACCESS_TOKEN` from `cloudflared` locally. Saved Cloudflare targets make `void secret`, `void domain`, `void project status|logs|rollback`, and remote `void db` commands operate directly; logs are live tailing. Rollback restores the selected version's saved schedules, queues, workflows, routes, and domains but never reverses database migrations; legacy versions without trigger snapshots are rejected. Direct commands target the root top-level Cloudflare config only; named environments, worker-bearing `--skip-build`, and node/bun/deno deploy targets fail closed. Avoid concurrent first deploys from different hosts because provisioning locks only the local config path.

Self-hosted lifecycle: installation requires a dedicated empty PostgreSQL database and transactionally claims it for one installation. Interactive administration uses Cloudflare browser OAuth with OS-keychain storage; the installed control plane receives a separate scoped runtime API token. Mutating lifecycle commands use the database claim for a cross-host advisory lock and store a secret-free authoritative lifecycle manifest in the claimed row. Local recovery checkpoints are AES-256-GCM encrypted with a key in the system keychain. After discovery elsewhere, export `VOID_PLATFORM_DATABASE_URL`; ordinary upgrades preserve deployed Worker secrets, while recreating a missing API or proxy Worker requires the original runtime, GitHub, R2, JWT, and project-encryption secrets. Existing runtime keys are never regenerated. `void platform disable [id]` durably gates traffic through installation-owned routing storage, repair and upgrade preserve that state, and `void platform enable [id]` restores it explicitly. Lifecycle redeploys preserve unmanaged Worker routes/custom domains and their rollback state, and stop before migrations or upload when Hyperdrive no longer matches the pinned database. Platform upgrades require exact packaged SQL hashes, an exact live migration prefix, and an explicit source-version/schema rollback edge before pending SQL; migrations are transactional and the old Worker version remains authoritative until target-version health passes. A locally built runtime can be supplied to install, upgrade, repair, or enable with `--runtime <directory>`; it receives the same integrity, migration, cutover, health, and rollback checks as the packaged runtime. Set `VOID_PLATFORM_SOURCE_REVISION` during its build to record a source commit in the installation checkpoint. Disable, enable, upgrade, repair, and uninstall verify remote and per-resource ownership before mutating Cloudflare; uninstall retains data unless `--purge-data` is supplied, and always retains name-addressed Workers, R2, AI Gateway, external PostgreSQL, and zones for explicit manual cleanup.

Full docs are in `node_modules/void/docs/`. If you have the `void` skill available, use it for a complete API reference covering project structure, routing, pages mode, database, auth, typed fetch, KV, storage, queues, cron jobs, email, CLI, configuration, and deployment.
